# Community 권한 정책 및 변경 내역

> 작성일: 2026-07-16  
> 상태: 적용 완료  
> 대상: Community 공개 API의 게시판, 게시글, 댓글·대댓글, 좋아요, 신고

## 1. 문서 목적

이 문서는 Community 도메인에 적용되는 현재 권한 정책을 팀의 공통 기준으로 정의하고,
정책 통일 전 구현과 비교해 달라진 동작을 정리한다.

정책 결정 전의 상세 점검 결과와 API별 과거 동작은
[`community-permission-audit.md`](./community-permission-audit.md)를 참고한다.

## 2. 권한 용어

| 용어 | 기준 |
| --- | --- |
| 시스템 관리자 | `User.roles`에 `Role.ADMIN`이 있는 사용자 |
| 게시판 관리자 | 해당 게시판의 `BoardAdmin` 목록에 등록된 사용자 |
| 전역 임원 | `Role.PRESIDENT` 또는 `Role.VICE_PRESIDENT`인 사용자 |
| 작성자 | 대상 게시글 또는 댓글의 `writer.id`와 요청 사용자의 ID가 같은 사용자 |
| 유효 사용자 | `UserState.ACTIVE`이고 `Role.NONE`을 보유하지 않은 사용자 |
| 생존 게시판 | `Board.isDeleted != true`인 게시판 |
| 생존 게시글 | 게시글과 상위 게시판이 삭제되지 않은 콘텐츠 |
| 생존 댓글·대댓글 | 댓글 자체와 상위 게시글·게시판이 삭제되지 않은 콘텐츠. 부모 댓글 삭제 여부는 대댓글 생존에 영향을 주지 않음 |

시스템 관리자와 게시판 관리자는 별개다. 시스템 관리자는 반드시 `Role.ADMIN`으로만
판정하며, 게시판 관리자는 반드시 해당 게시판의 `BoardAdmin` 등록 여부로 판정한다.

## 3. 현재 권한 정책

### 3.1 공통 사용자 조건

Community 공개 API에서 게시판 목록, 게시글·댓글 조회와 변경, 좋아요 생성·취소를
수행하려면 유효 사용자여야 한다.

- `UserState.ACTIVE`가 아니면 허용하지 않는다.
- `Role.NONE`을 가진 사용자는 허용하지 않는다.
- 위 조건은 목록과 상세, 변경 API에서 동일하게 적용한다.

### 3.2 게시판 읽기

먼저 게시판이 삭제되지 않아야 한다.

| 요청자 | `VISIBLE` | `HIDDEN` | `readScope` |
| --- | --- | --- | --- |
| 일반 사용자 | 허용 | 거부 | 반드시 충족 |
| 게시판 관리자 | 허용 | 허용 | 우회 |
| 시스템 관리자 | 허용 | 허용 | 우회 |
| 게시글 작성자 | 일반 사용자 정책 적용 | 별도 우회 없음 | 별도 우회 없음 |

게시판 읽기 가능 목록, 게시글 일반·개인 목록, 게시글 상세, 댓글 목록은 모두 이 기준을
공유한다.

### 3.3 게시글·댓글 작성

작성은 다음 조건을 모두 충족해야 한다.

1. 요청자가 유효 사용자다.
2. 게시판과 상위 게시글이 삭제되지 않았다.
3. 요청자에게 게시판 읽기 권한(`canRead`)이 있다.
4. 게시판의 `writeScope`를 충족한다.

시스템 관리자와 게시판 관리자는 `readScope`와 `writeScope`를 우회할 수 있다. 단,
`HIDDEN` 게시판에는 시스템 관리자, 게시판 관리자, 기존 작성자를 포함해 누구도 새
게시글·댓글·대댓글을 작성할 수 없다.

댓글·대댓글의 익명 여부에는 게시판의 `isAnonymous` 설정을 추가로 강제하지 않는다.

삭제된 루트 댓글은 답글의 부모로 사용할 수 있다. 이 경우에도 상위 게시글·게시판은
생존 상태여야 하고, 요청자는 게시판 읽기·쓰기 권한을 모두 충족해야 한다. 대댓글을
부모로 지정해 2단계보다 깊은 답글을 작성하는 것은 삭제 여부와 관계없이 허용하지 않는다.

### 3.4 수정·삭제 권한

모든 변경은 대상과 상위 게시글·게시판이 생존해 있고, 요청자가 대상을 읽을 수 있을
때만 허용한다.

| 주체 | 게시글 수정 | 게시글 삭제 | 댓글·대댓글 수정 | 댓글·대댓글 삭제 |
| --- | --- | --- | --- | --- |
| 작성자 | O | O | O | O |
| 해당 게시판 관리자 | X | O | X | O |
| 시스템 관리자 | X | O | X | O |
| 회장·부회장 | X | O | X | O |
| 일반 사용자 | X | X | X | X |

역할은 작성자 권한을 없애지 않는다. 예를 들어 시스템 관리자가 자신이 작성한 게시글을
수정하는 것은 작성자 자격으로 허용된다. 회장·부회장에게는 읽기 우회 권한이 없으므로,
현재 읽을 수 없는 콘텐츠는 삭제할 수 없다.

게시글 삭제 API는 이미 삭제된 게시글에 다시 요청해도 성공으로 처리하는 멱등 동작을
유지한다.

### 3.5 삭제 상태

상위 리소스 삭제와 댓글 자체 삭제는 다음과 같이 처리한다.

| 삭제 대상 | 함께 삭제 상태로 변경 | 상태를 보존하는 데이터 | 공개 동작 |
| --- | --- | --- | --- |
| 게시판 | 소속 게시글, 게시글에 연결된 폼 | 댓글·대댓글, 좋아요, 신고 | 게시판 및 모든 하위 콘텐츠 접근 불가 |
| 게시글 | 게시글에 연결된 폼 | 댓글·대댓글, 좋아요, 신고 | 목록·상세·개인 목록·댓글·좋아요·신고 접근 불가 |
| 루트 댓글 | 없음 | 기존 대댓글, 좋아요, 신고 | tombstone으로 조회되며 새 대댓글 작성만 허용 |
| 대댓글 | 없음 | 좋아요, 신고 | tombstone으로 조회되며 변경·반응 불가 |

삭제 댓글·대댓글은 목록에서 제거하지 않고 다음 tombstone 계약으로 반환한다.

- `isDeleted=true`, `content=null`
- 작성자 실명·닉네임·입학연도는 노출하지 않고 익명/GHOST 프로필을 사용한다.
- `updatable=false`, `deletable=false`
- ID, 작성·수정 시각, 기존 좋아요 수와 현재 사용자의 좋아요 여부는 유지한다.
- 삭제된 대상 자체의 수정·재삭제·좋아요 생성·취소·신고는 허용하지 않는다.

삭제된 루트 댓글 아래의 미삭제 대댓글은 정상 콘텐츠다. 조회·수정·삭제·좋아요·신고가
가능하고, 같은 삭제 루트 댓글에 새 대댓글도 작성할 수 있다.

댓글 개수는 용도에 따라 다음 기준을 사용한다.

| 필드 | 집계 기준 |
| --- | --- |
| 게시글 `numComment` | 미삭제 댓글·대댓글만 포함 |
| 댓글 페이지 `totalElements` | tombstone을 포함한 루트 댓글 수 |
| 루트 댓글 `numChildComment` | tombstone을 포함해 응답에 포함되는 대댓글 수 |

### 3.6 게시글 목록과 상세 응답의 권한 필드

게시글 일반 목록과 개인 목록에서도 상세 응답과 동일하게 다음 필드를 제공한다.

- `isOwner`: 작성자 표시만을 위한 값
- `updatable`: 실제 게시글 수정 API와 같은 정책으로 계산한 값
- `deletable`: 실제 게시글 삭제 API와 같은 정책으로 계산한 값

`isOwner`를 수정·삭제 권한의 대체 값으로 사용하지 않는다. 권한 필드는 유효 사용자,
대상·상위 리소스의 삭제 상태, 게시판 읽기 권한과 숨김 상태를 통과한 콘텐츠에 대해서만
계산한다. 댓글·대댓글 응답도 동일한 공통 권한 계산을 사용한다.

### 3.7 차단 관계

일반 사용자가 차단한 작성자의 게시글은 다음 경로에서 접근할 수 없다.

- 일반 게시글 목록 및 개인 게시글 목록
- 게시글 상세
- 해당 게시글의 댓글 목록과 댓글 작성
- 해당 게시글 또는 댓글에 대한 좋아요 생성

해당 게시판 관리자와 시스템 관리자는 moderation 목적으로 차단 관계를 우회할 수 있다.
회장·부회장과 게시글 작성자에게는 별도 차단 우회 권한을 부여하지 않는다.

### 3.8 좋아요

| 동작 | 읽기 권한 | 대상·상위 리소스 생존 | 차단 관계 |
| --- | --- | --- | --- |
| 게시글·댓글 좋아요 생성 | 필요 | 필요 | 적용 |
| 게시글·댓글 좋아요 취소 | 재검사하지 않음 | 필요 | 재검사하지 않음 |

따라서 좋아요 생성 후 게시판 범위가 바뀌거나 차단 관계가 생겨 읽기 권한을 잃더라도,
대상과 상위 리소스가 삭제되지 않았다면 본인의 좋아요는 취소할 수 있다.

## 4. 이전 정책과 달라진 점

| 영역 | 이전 구현 | 현재 구현 |
| --- | --- | --- |
| 유효 사용자 | API마다 상태·`Role.NONE` 검사 여부가 달랐음 | 모든 Community 공개 동작에서 `ACTIVE`이고 `Role.NONE`이 없어야 함 |
| 게시판 읽기 목록 | 일반 사용자 scope와 `VISIBLE`만 적용, 관리자 우회 없음 | 목록·직접 조회 모두 동일한 정책이며 시스템/해당 게시판 관리자 우회 적용 |
| 게시판 쓰기 목록 | 실제 작성 검증과 학적·숨김 조건이 달랐음 | 실제 작성과 같은 `canRead + writeScope` 정책 사용 |
| `HIDDEN` 쓰기 | 실제 게시글 작성 경로에서는 가능할 수 있었음 | 모든 주체의 게시글·댓글·대댓글 작성 금지 |
| 일반 게시글 목록 | 명시적 `boardIds` 여부에 따라 관리자 우회와 검증이 달랐음 | 쿼리 단계에서 공통 읽기·삭제·차단 정책 적용 |
| 개인 게시글 목록 | 현재 게시판 권한과 삭제 게시판을 확인하지 않았음 | 일반 목록과 같은 현재 읽기 권한 적용 |
| 게시글 상세 | 삭제 게시글·삭제 게시판이 조회될 수 있었음 | 생존 리소스와 공통 읽기 정책을 모두 요구 |
| 댓글 목록·작성 | 게시판 `readScope`, `visibility`를 확인하지 않았음 | 상위 게시글 `canRead` 필수, 작성에는 게시판 `writeScope`도 필수 |
| 게시글 수정·삭제 | 상세 응답 플래그와 실제 API 기준이 부분적으로 달랐음 | 공통 계산기로 작성자·관리자·임원 정책 통일 |
| 댓글 수정·삭제 | 응답 플래그와 실제 검증이 달랐고 삭제 주체 검증이 부족했음 | 수정은 작성자만, 삭제는 작성자·해당 게시판 관리자·시스템 관리자·회장·부회장 |
| 목록 응답 | 게시글 목록에는 `isOwner`만 있어 실제 권한을 표현하지 못했음 | `updatable`, `deletable` 추가, 상세와 같은 정책 사용 |
| 차단 | 목록과 상세, 댓글 경로 및 관리자 우회가 서로 달랐음 | 모든 읽기 경로에 적용, 해당 게시판 관리자와 시스템 관리자만 우회 |
| 게시판 삭제 | V2 삭제 시 소속 게시글 일괄 삭제가 누락됨 | 게시판, 소속 게시글, 연결 폼을 함께 소프트 삭제 |
| 삭제 댓글 목록 | 계층 통합 후 삭제 댓글과 그 대댓글이 목록에서 사라짐 | 삭제 댓글·대댓글을 tombstone으로 유지 |
| 삭제 부모의 대댓글 | 부모 삭제 시 미삭제 대댓글도 변경·반응 불가 | 미삭제 대댓글은 정상 동작하며 새 대댓글 작성도 허용 |
| 삭제 플래그 | Post·Comment의 `NULL`을 경로별로 다르게 해석 | 기존 `NULL`을 `false`로 정규화하고 두 상태만 허용 |
| 좋아요 생성 | 대상의 현재 읽기 권한을 보장하지 않았음 | 읽기 권한, 생존 상태, 차단 관계를 모두 검사 |
| 좋아요 취소 | 접근 권한 변화에 따른 정책이 명확하지 않았음 | 읽기는 재검사하지 않고 대상 생존만 요구 |

## 5. API 영향

주요 적용 대상은 다음과 같다.

- `GET /api/v2/boards/available`
- `GET /api/v2/boards/writable`
- `POST /api/v2/posts`
- `GET /api/v2/posts`
- `GET /api/v2/posts/me`
- `GET /api/v2/posts/me/liked`
- `GET /api/v2/posts/me/commented`
- `GET /api/v2/posts/{postId}`
- `PUT /api/v2/posts/{postId}`
- `DELETE /api/v2/posts/{postId}`
- `GET /api/v2/comments?postId={postId}`
- 댓글·대댓글 생성, 수정, 삭제, 좋아요 생성·취소 API

클라이언트 응답 계약에서 게시글 목록 항목에 `updatable`, `deletable`이 추가된다. 기존
`isOwner`는 유지하지만 화면 표시 외의 권한 판단에는 사용하지 않아야 한다.

## 6. 구현 기준점

권한 판단은 `CommunityPermissionPolicy`를 단일 기준으로 사용한다.

- 게시판 목록은 `BoardAccessManager`가 공통 정책으로 필터링한다.
- 게시글 일반·개인 목록은 `PostReadQueryContext`를 사용해 DB 조회 단계에서 같은 읽기
  정책을 적용한다.
- 게시글·댓글 validator와 응답 mapper는 공통 정책을 호출한다.
- 차단은 서비스 경계와 게시글 목록 쿼리에서 적용하며, moderation 우회 주체를 동일하게
  판정한다.

정책을 변경할 때는 목록 쿼리, 상세 validator, 응답 권한 필드 중 하나만 수정하지 말고
공통 정책과 관련 회귀 테스트를 함께 변경해야 한다.
