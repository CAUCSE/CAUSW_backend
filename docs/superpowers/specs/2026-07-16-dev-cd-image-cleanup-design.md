# Dev CD 로컬 Docker 이미지 정리 설계

## 배경

`dev-cd-docker.yml`은 배포마다 애플리케이션 이미지와 Flyway migration 이미지를 EC2에 pull한다. 배포 마지막에 실행하는 `docker image prune -f`는 dangling 이미지만 제거하므로, 커밋 SHA 태그가 붙은 과거 애플리케이션 이미지와 migration 이미지가 EC2에 계속 남는다.

## 목표

- EC2 로컬에서 현재 실행하는 애플리케이션 이미지를 보존한다.
- 롤백을 위해 직전에 실행하던 애플리케이션 이미지 한 개를 보존한다.
- Flyway가 끝나고 새 컨테이너가 실행된 후, 같은 ECR 저장소에서 가져온 나머지 이미지와 migration 이미지를 삭제한다.
- EC2에 존재하는 다른 저장소의 Docker 이미지는 변경하지 않는다.
- ECR 원격 저장소의 이미지는 변경하지 않는다.

## 범위 밖

- ECR Lifecycle Policy 설정
- ECR 원격 이미지 삭제
- 배포 실패 시 자동 롤백
- 다른 Docker 저장소의 이미지 또는 dangling 이미지 정리

## 선택한 방식

배포 단계에서 Docker 이미지 ID를 이용한 보호 목록을 구성한다.

1. SSH 스크립트 시작 시 `set -euo pipefail`을 적용해 명령 실패 후 정리 단계가 계속 실행되지 않게 한다.
2. 기존 애플리케이션 컨테이너를 제거하기 전에 `docker inspect`로 직전 이미지 ID를 저장한다.
3. 이번 배포에서 pull한 이미지의 ID를 `docker image inspect`로 저장한다.
4. 기존 컨테이너를 중지·제거하고 새 이미지로 컨테이너를 실행한다.
5. `IMAGE`에서 태그를 제거해 애플리케이션의 전체 ECR 저장소 이름을 구한다.
6. 해당 저장소의 로컬 이미지 레퍼런스만 조회한다.
7. 현재 이미지 ID와 직전 이미지 ID가 아닌 레퍼런스를 삭제한다.

시간이나 태그 개수가 아니라 실제 컨테이너 이미지 ID를 기준으로 하므로, 배포 간격이나 태그 이름에 관계없이 보존 대상 두 개를 결정할 수 있다.

## 삭제 범위 제한

삭제 후보는 다음 명령의 결과로 제한한다.

```bash
IMAGE_REPOSITORY="${IMAGE%:*}"
docker image ls "$IMAGE_REPOSITORY" \
  --no-trunc \
  --format '{{.Repository}}:{{.Tag}} {{.ID}}'
```

따라서 다른 ECR 저장소나 Docker Hub에서 받은 이미지에는 삭제 명령을 실행하지 않는다. 전역 범위에 영향을 줄 수 있는 `docker image prune -f`는 제거한다.

## 예외 및 실패 처리

- 첫 배포처럼 기존 컨테이너가 없으면 직전 이미지 ID는 빈 값이며 현재 이미지만 보존한다.
- 동일한 커밋을 재배포해 현재와 직전 이미지 ID가 같아도 해당 이미지가 보존된다.
- 새 컨테이너 실행이 실패하면 `set -euo pipefail`에 의해 셸 실행이 중단되어 이미지 정리 단계에 도달하지 않는다.
- 이미지 조회 또는 삭제가 예상치 못하게 실패하면 배포 단계도 실패하도록 처리한다. 삭제 오류를 무시하지 않아 디스크 정리가 실제로 수행됐는지 확인할 수 있게 한다.
- 이미지 ID 비교에는 `--no-trunc` 결과를 사용해 축약 ID 비교 오류를 방지한다.

## 대안

### `docker image prune -a`

사용하지 않는 이미지를 간단히 삭제할 수 있지만, 컨테이너 제거 후 직전 이미지도 함께 삭제하며 다른 저장소 이미지까지 영향을 줄 수 있어 사용하지 않는다.

### 생성 시각 또는 보존 개수 기준

이미지를 생성 시각순으로 정렬해 두 개만 남길 수 있지만, 애플리케이션 이미지와 migration 이미지가 섞이고 재배포 시각에 따라 잘못된 이미지가 보존될 수 있어 사용하지 않는다.

### 로컬 `previous` 태그 추가

직전 이미지에 별도 태그를 붙이는 방식은 사람이 알아보기 쉽지만, 가변 태그 상태를 추가로 관리해야 한다. 실제 실행 컨테이너에서 이미지 ID를 직접 얻는 방식이 더 단순하므로 사용하지 않는다.

## 검증

워크플로 변경 후 다음 시나리오를 셸 명령 수준에서 검증한다.

- 기존 컨테이너가 없는 첫 배포에서 현재 이미지가 남는다.
- 기존 컨테이너가 있는 배포에서 현재 이미지와 직전 이미지가 남는다.
- migration 이미지와 두 세대보다 오래된 애플리케이션 이미지가 삭제된다.
- 다른 저장소의 이미지가 삭제되지 않는다.
- 동일한 이미지를 재배포해도 현재 이미지가 삭제되지 않는다.
- 새 컨테이너 실행 실패 시 정리 단계가 실행되지 않는다.
